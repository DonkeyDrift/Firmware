# ESP32 上行遥测频率设计分析

## 概述

ESP32 固件通过 Serial1 向上位机发送三类上行帧，频率各不相同：

| 帧类型 | 频率 | 间隔 | 触发条件 |
|--------|------|------|----------|
| `T{thr}S{str}\n` | ~60Hz | 16ms | 仅 MANUAL 模式 |
| `$IMU,...` | ~100Hz | 10ms | 所有模式持续发送 |
| `M{m}:P{p}\n` | 1Hz + 即时 | 1000ms / 状态变化即时 | 所有模式 |

本文档分析控制遥测 (60Hz) 与 IMU (100Hz) 频率差异的设计依据、收益与代价。

## 频率为什么不同

### 1. 数据源决定上限

| 帧类型 | 频率 | 数据源 | 源采样率 |
|--------|------|--------|----------|
| `T...S...` | ~60Hz | RC 接收机 PWM 脉冲 | 标准 RC 接收机帧率 50–60Hz |
| `$IMU` | ~100Hz | MPU6050 (I2C) | `SENSOR_UPDATE_INTERVAL=2ms` → 500Hz 轮询，芯片最高支持 250Hz |

RC 接收机每 16ms 输出一帧 PWM 脉冲，固件侧 `RC_DATA_UPDATE_INTERVAL=16ms` 与此对齐。发送比 60Hz 更快没有意义——数据源本身不更新，多出来的帧全是重复值。

IMU 是 MEMS 传感器，物理采样率天然可达数百 Hz。固件以 2ms 间隔轮询 MPU6050（~500Hz），选取 100Hz 作为上行频率是在精度与带宽之间的折中。

### 2. 下游模型需求不同（核心原因）

`FirmwareConfig.h` 中的注释点明了关键设计意图：

```c
#define IMU_TELEMETRY_INTERVAL_MS 10 // Serial1 $IMU 帧节奏 (ms) - ~100Hz，对齐上位机 GRU W=16 ring buffer
```

IMU 数据服务于**漂移动力学模型**（KerasIMU / GRU）。漂移过程中车辆的横摆角速度 (gyro_z) 和侧向加速度 (accel_y) 变化极快：

- **100Hz + W=16 ring buffer** → 160ms 时间窗口，16 个时间步，足够的时序粒度捕捉一次完整漂移的状态演化
- 如果降到 60Hz，同样 W=16 的窗口会拉长到 267ms，**时间分辨率下降 1.67 倍**，模型对高速漂移的瞬态响应会明显退化
- IMU 帧携带 `ts_ms` 毫秒级时间戳，上位机可以精确插值对齐，不受串口到达抖动影响

控制遥测 (`T...S...`) 记录的是**人类驾驶员的输入**。人手操作的带宽远低于车辆动力学响应——人类反应极限约 200ms，60Hz (16ms) 早已超出此阈值数倍，够用且有充分余量。该帧的核心价值在于：
- 记录训练标签（人类驾驶员的油门/转向作为监督信号）
- MANUAL 模式下实时回传控制状态供上位机显示

### 3. 过采样架构

三层频率形成一个**过采样金字塔**：

```
数据源                   ESP32 上行           Linux 上位机
──────────────────────────────────────────────────────────
MPU6050                  $IMU                 ArdImu.update()
~500Hz 轮询 ──▶ 100Hz ──────▶ Serial1 ──▶ 100Hz 轮询缓存
                                           │
RC 接收机                T...S...             Arduino_readline()
~60Hz ──────▶ 60Hz ───────▶ Serial1 ──▶ 按行解析控制 dict
                                           │
                                     Vehicle 主循环 20Hz
                                     读取 Memory 最新值
                                     TubWriter 20Hz 录制
```

上位机 Vehicle 主循环以 20Hz (`DRIVE_LOOP_HZ`) 运行，但 Serial1 上的数据以更高频率持续刷新 Memory 缓存。这意味着：
- Vehicle 每次读取 IMU 数据时，缓存中的值最多只有 10ms 的陈旧延迟
- 如果 IMU 也是 20Hz，最差情况下数据已陈旧 50ms
- 对漂移控制而言，10ms vs 50ms 的感知延迟差异显著

## 好处

### 感知延迟低

IMU 以 100Hz 刷新，Vehicle 循环 20Hz 每次读到的 IMU 数据陈旧度 ≤10ms。如果 IMU 也按 20Hz 发送，最差情况陈旧度达 50ms。在高速漂移场景下，40ms 的延迟差异意味着模型决策依据的车辆状态偏差不可忽略。

### 带宽合理分配

如果两路都按 100Hz 发，T...S... 帧纯属浪费——数据源只有 60Hz，多出来的 40% 是重复值。三路帧总带宽约 160Hz（100+60+心跳），115200 波特率下每帧几十字节，串口带宽充裕。

### 时序对齐灵活

IMU 帧携带独立的毫秒级时间戳 (`ts_ms`) 和序列号 (`seq`)，上位机 `Collator` 构建 RNN 序列时可以精确插值对齐到 Vehicle 主循环的时间步，不依赖串口帧的到达时刻。

### 录制与推理解耦

固件侧 IMU 频率 (100Hz) 独立于上位机录制频率 (20Hz)。未来如果需要更高时间分辨率的录制，只需调整上位机 `DRIVE_LOOP_HZ` 或 TubWriter 策略，固件侧无需改动。

## 坏处

### 多路复用的到达抖动

三路帧共享 Serial1 物理通道，帧到达顺序不可预测。一个 `$IMU` 帧（约 80 字节）正在发送时，如果恰好到了 `T...S...` 的发送时刻，后者必须排队等待当前帧发送完成。100Hz IMU 帧占据大部分串口时间片，控制帧偶尔会有 1–2ms 的发送延迟。

缓解措施：固件中 IMU 帧使用 `Serial1.write()` 一次性写入栈缓冲，避免 `String` 拼接造成的堆分配抖动（v1.7.15 优化）。

### Tub 录制丢失高频信息

Vehicle 循环 20Hz 录制意味着每 50ms 只取一个 IMU 快照。100Hz 原始流中 80% 的 IMU 样本在录制时被丢弃。如果后续训练需要更高时间分辨率的动力学数据（例如高频振动分析、碰撞检测），需要：
- 在 ESP32 侧增加本地环形缓冲（当前未实现）
- 或提升上位机录制率（会显著增大 Tub 体积）

### 调试复杂度

两路帧频率不同意味着时序分析时需要区分对待：
- IMU 丢帧检测：100Hz 下 10ms 间隔，对串口抖动更敏感
- 控制帧丢帧检测：60Hz 下 16ms 间隔，更容易被上位机觉察（因为直接影响操控手感）
- 排查时需要在时间轴上分别对两路做丢帧统计，不能混用同一阈值

## 配置参考

```c
// FirmwareConfig.h — ESP32 固件侧
#define RC_DATA_UPDATE_INTERVAL 16     // T...S... 帧间隔 (ms) — ~60Hz
#define IMU_TELEMETRY_INTERVAL_MS 10   // $IMU 帧间隔 (ms) — ~100Hz
#define MODE_PARK_HEARTBEAT_MS 1000    // M:P 心跳间隔 (ms) — 1Hz
#define SENSOR_UPDATE_INTERVAL 2       // I2C 传感器轮询间隔 (ms) — ~500Hz
```

```python
# cfg_complete.py — DonkeyDrift 上位机侧
DRIVE_LOOP_HZ = 20                    # Vehicle 主循环频率
```
