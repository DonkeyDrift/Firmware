# 漂移裁判系统 Judge 监控优先 UI 设计

## 背景

前一轮已经完成漂移裁判系统的第一阶段数据接入：

- 固件侧新增了 `pseudoSpeed`，作为基于 `|gyro_z| + throttle` 计算出的评分代理速度。
- `/api/data` 与 WebSocket `latest` 已输出 `pseudoSpeed`。
- 主固件内已经存在 `/judge` 路由，但当前页面仍是一个最小骨架，只展示 `pseudoSpeed`、`gyroZ`、`throttle` 与 `seq`。

当前缺口不再是底层数据链路，而是 Judge 页面本身仍未承载原型评分系统的核心价值：

- 缺少监控优先的调参视图。
- 缺少实时总分与 6 个维度评分。
- 缺少开始/结束计分与重置的评分状态机。
- 仍未把 `Ref/app.js` 中依赖 `speed` 的核心评分逻辑切换到 `pseudoSpeed`。

用户已明确确认：

- 本轮页面方向选择 `C`，即“监控优先”。
- 但同时保留实时总分计算，而不是只做纯监控页。

## 目标

- 将 `/judge` 从 latest 预览页升级为“监控优先的最小可用评分页”。
- 页面第一视觉层优先展示 `pseudoSpeed` 与 `gyroZ` 的观测与调参信息。
- 保留实时总分和 6 个评分维度，使页面同时具备监控和评分能力。
- 保留“开始/结束计分”与“重置”两项核心交互。
- 以主固件 WebSocket 遥测作为 `/judge` 的主数据通路，并保留 `/api/data?since=...` 作为兜底回退链路。

## 非目标

- 不迁回 `SSE + SPIFFS + 独立 AP` 原型架构。
- 不在本轮启用独立 `app.js` 资源文件，仍沿用内嵌到 `WebConsoleAssets.h` 的资产方式。
- 不在本轮加入历史记录面板。
- 不在本轮加入权重调节滑块。
- 不在本轮新增独立于现有控制台之外的第二套 WebSocket 协议。
- 不在本轮提供实车参数标定或碰撞阈值调参 UI。

## 方案对比

### 方案 1：HTTP 轮询 + 监控优先评分页

- `/judge` 继续通过 `/api/data?since=...` 获取 `latest` 与增量点。
- 页面内部完成监控视图、评分状态机和 6 维评分计算。
- 这是改动最保守的方案。

优点：

- 基于现有骨架页增量演进，风险最低。
- UI 迁移与传输层改动解耦，便于验证问题来源。
- 便于先验证 `pseudoSpeed` 在评分层是否“手感正确”。

缺点：

- 刷新频率上限受轮询节奏限制。
- 曲线观感不如 WebSocket 平滑。

### 方案 2：WebSocket 驱动 + 监控优先评分页

- Judge 页面直接切换到 WebSocket `latest` 与增量点驱动。
- 同时迁入 UI 与评分逻辑。
- HTTP `/api/data?since=...` 保留为断线或握手失败时的兜底回退路径。

优点：

- 实时性更好，曲线表现更平滑。
- 后续更适合高频调试。

代价：

- 本轮会把 UI 迁移与传输层适配绑在一起。
- 若出现显示或评分异常，定位成本更高。

### 方案 3：纯监控页，评分延后

- 本轮只做 `pseudoSpeed` 与 `gyroZ` 监控，不做总分与 6 维评分。

优点：

- 风险最低。
- 最利于先做数据观测。

缺点：

- 会把评分主链路再拆成下一轮。
- 用户已确认本轮仍要保留实时总分计算，因此不符合当前目标。

## 最终决策

本轮采用“WebSocket 驱动 + 监控优先评分页”的方案，保留实时总分计算，并将 HTTP 轮询保留为兜底回退路径。总分区仍从页面主视觉降为次要信息块。

## 页面结构

### 总体布局

`/judge` 页面按“监控优先”组织为 5 个区域：

1. 顶部状态区
2. `pseudoSpeed` 主监控区
3. `gyroZ` 曲线与 latest 观测区
4. 总分与等级区
5. 6 个评分维度 + 控制按钮区

### 1. 顶部状态区

展示：

- 连接状态
- 当前 `seq`
- 返回 `/` 的入口

设计意图：

- 保留现有骨架页的连接反馈。
- 让调试时能快速判断是否有新样本进入。

### 2. `pseudoSpeed` 主监控区

页面第一视觉区域以 `pseudoSpeed` 为核心，采用更大号数值和横向条形图。

展示：

- `pseudoSpeed` 当前值
- `0~100` 可视化进度条
- 当前监控状态标签，例如 `online`、`waiting data`、`offline`

设计意图：

- 强化 `pseudoSpeed` 作为本系统核心代理量的定位。
- 让用户在实车调试时一眼看到动作强度变化。

### 3. `gyroZ` 曲线与 latest 观测区

在 `pseudoSpeed` 主区下方展示轻量监控区，包含：

- `gyroZ` 最新值
- `throttle` 最新值
- 一段轻量 `gyroZ` 曲线

数据来源以 WebSocket 推送的 `latest` 和增量点为主；若 WebSocket 不可用，则退回 `/api/data?since=...` 拉取，不再新增第三条接口。

设计意图：

- 保留对转向动态的直接观测。
- 帮助判断 `pseudoSpeed` 的变化是否与姿态变化一致。

### 4. 总分与等级区

保留总分与等级，但退居第二视觉层，不再复用原型中居中的大圆环主视觉。

展示：

- 实时总分
- 当前等级
- 碰撞扣分后的即时结果

设计意图：

- 满足“本轮仍保留实时总分”的要求。
- 避免总分视觉权重压过监控功能。

### 5. 6 个评分维度与控制按钮区

展示：

- 6 个维度条形评分
- “开始/结束计分”按钮
- “重置”按钮

本轮不展示：

- 历史记录面板
- 权重调节区

设计意图：

- 先保证最小可用评分页闭环。
- 把不影响核心验证的功能留到下一轮。

## 评分状态机

Judge 页面维护两个主要状态：

- `idle`
- `running`

### `idle`

行为：

- 页面继续接收并展示实时监控数据。
- 不累计评分样本。
- 总分与 6 维评分保持最近一次结果或初始状态。

### `running`

行为：

- 每次收到有效样本后更新评分窗口。
- 累加 6 个维度的统计值。
- 实时刷新总分、等级与碰撞状态。

### 结束计分

当用户点击“结束计分”后：

- 停止继续累加评分。
- 保留页面上的本次最终结果。
- 不在本轮写入历史记录列表。

### 重置

当用户点击“重置”后：

- 清空评分累计值与样本窗口。
- 清空碰撞计数与临时状态。
- 页面回到初始待命状态。

## 数据模型

页面消费的核心字段如下：

- `latest.seq`
- `latest.gz`
- `latest.thr`
- `latest.pseudoSpeed`

主通路为 WebSocket 二进制遥测：

- 页面连接现有数据 WebSocket。
- 复用已经扩展过的 `latest.pseudoSpeed` 解码结果。
- 若消息中携带增量 `points`，则用于驱动轻量曲线与窗口更新。

兜底通路为 HTTP：

- 当 WebSocket 握手失败、连接关闭或解析异常时，页面回退到 `/api/data?since=...`。
- 回退后仍保持相同的评分状态机与 UI 更新逻辑。
- 若后续 WebSocket 恢复，可按现有控制台模式重新接管主通路。

无论使用哪条通路，若某次仅拿到 `latest`，页面也必须能独立工作。

页面内部状态至少包含：

- 最近一段 `gyroZ` 样本窗口
- 最近一段 `pseudoSpeed` 样本窗口
- 最近一段 `throttle` 样本窗口
- 当前运行状态
- 当前总分
- 当前 6 维均分
- 碰撞冷却状态

这些状态仅保存在前端内存，不回写固件。

## 6 个评分维度映射

本轮保留原有 6 个维度名称，但把内部依赖 `speed` 的部分切换为 `pseudoSpeed`。

### 1. 转弯平滑

- 输入：最近窗口内的 `gyroZ`
- 逻辑：观察相邻样本变化率与突变程度
- 含义：动作越顺滑，得分越高

### 2. 区间匹配

- 输入：`pseudoSpeed` 与 `|gyroZ|`
- 逻辑：由原先“速度与角速度匹配”改为“代理速度与角速度匹配”
- 含义：漂移动作强度和动态支撑越协调，得分越高

### 3. 陀螺稳定

- 输入：短窗口 `gyroZ`
- 逻辑：依据窗口内方差或标准差评分
- 含义：陀螺输出越稳定，得分越高

### 4. 大弯稳定

- 输入：进入大弯阈值后的 `gyroZ` 窗口
- 逻辑：当 `|gyroZ|` 超过阈值后进入“大弯区”，单独评估该阶段稳定性
- 含义：大动作阶段越稳定，得分越高

### 5. 速度稳定

- 输入：短窗口 `pseudoSpeed`
- 逻辑：由原 `speed` 稳定改为 `pseudoSpeed` 稳定
- 含义：整段动作强度越持续、越不忽高忽低，得分越高

### 6. 油门稳定

- 输入：短窗口 `throttle`
- 逻辑：评估油门波动程度
- 含义：油门越平顺，得分越高

## 总分计算

- 每个维度输出 `0~100`。
- 本轮采用固定等权平均。
- 不在本轮暴露权重调节入口。

这意味着本轮重点是先验证“基于 `pseudoSpeed` 的评分模型是否可用”，而不是同时开放复杂调参面板。

## 碰撞处理

保留 `Ref/app.js` 中“陀螺突变触发碰撞提示”的总体思路，但基于当前固件量纲重做阈值收敛。

### 规则

- 对比当前 `gyroZ` 与上一有效样本的差值。
- 若差值超过阈值，则触发碰撞提示。
- 碰撞触发后进入短暂冷却，避免单次碰撞连续重复扣分。
- 仅在 `running` 状态下应用扣分。

### 本轮边界

- 阈值先采用可工作的经验值。
- 不新增固件侧碰撞字段。
- 不提供阈值 UI 调节。

## 异常处理

### 连接异常

若 WebSocket 建连失败或运行中断开：

- 页面显示 `offline` 或等价状态。
- 保留最后一次有效监控值。
- 启动 HTTP 轮询兜底。
- 不自动清空当前总分和监控图。

若 HTTP 兜底请求也失败：

- 页面继续显示 `offline`。
- 保持最后一次有效值，等待后续重连。

### 数据缺失

若 `latest` 缺字段、字段非法或无新 `seq`：

- 跳过该次样本的评分写入。
- 保留页面当前显示值。
- 避免异常值污染窗口统计。

### 等待数据

若 WebSocket 已连接但短时无新样本，或 HTTP 接口正常返回但暂无新样本：

- 页面显示 `waiting data`。
- 继续保持连接状态正常。
