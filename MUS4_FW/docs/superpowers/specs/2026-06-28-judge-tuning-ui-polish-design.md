# Judge 调参区 UI 微调设计

## 背景

当前 `/judge` 已完成两轮能力扩展：

- 第一批持久化参数：
  - `collisionThreshold`
  - `bigTurnThreshold`
  - `windowSize`
- 第二批持久化参数：
  - `collisionPenalty`
  - `turnSmoothnessWeight`
  - `rangeMatchWeight`
  - `gyroStabilityWeight`
  - `bigTurnStabilityWeight`
  - `speedStabilityWeight`
  - `throttleStabilityWeight`

这些能力已经满足“设备侧持久化 + 页面实时调参”的核心目标，但随着参数数量增加，当前 `/judge` 调参区开始出现以下问题：

- 参数分组不够明显，用户难以一眼区分“判定边界”和“评分手感”
- 第二批参数平铺后信息密度偏高，尤其在移动端和实车环境下不够好用
- 参数名称虽然准确，但对现场调参来说解释还不够直接
- 保存和恢复默认值的反馈还可以更醒目，更适合边调边试

用户已明确确认：

- 下一步优先做 UI 微调
- 这轮只做调参区易用性优化
- 不改评分逻辑
- 不扩参数数量
- 不改后端接口

因此，本轮目标是提升 `/judge` 调参区在现场使用时的可读性和可操作性，而不是继续扩能力。

## 目标

- 让用户快速识别“基础阈值”和“评分参数”两类配置
- 降低第二批参数在移动端上的视觉拥挤程度
- 通过短提示文案降低参数理解门槛
- 让保存和恢复默认值的结果反馈更直观
- 保持现有后端接口与评分逻辑不变

## 非目标

- 不增加新参数
- 不改变现有评分公式
- 不引入滑块控件
- 不增加新的可视化图表
- 不改 WebSocket / HTTP 数据链路
- 不增加新的持久化字段

## 方案对比

### 方案 1：现有表单轻量重排 + 中文提示增强

- 保持当前输入框形态
- 优化参数分组与布局
- 补充简短提示文案
- 优化状态反馈

这是本轮推荐方案。

优点：

- 改动小
- 不影响接口和逻辑
- 很适合当前“只做 UI 微调”的范围

缺点：

- 仍然是输入框方案，交互形式没有根本变化

### 方案 2：滑块化改造

- 将大部分参数从输入框改为滑块

优点：

- 看起来更“像调参台”
- 某些参数在手机上拖动更直观

缺点：

- 精确输入变差
- 改动更大
- 不符合本轮“只做轻量 UI 微调”的边界

### 方案 3：调参与图形反馈联动增强

- 一边显示表单，一边增加可视化预览块

优点：

- 用户能更直观理解参数影响

缺点：

- 范围明显扩大
- 会把这轮变成“实时反馈增强”而不是 UI 微调

## 最终决策

本轮采用方案 1：

- 不改变输入方式
- 只优化布局、分组、文案与反馈
- 保持后端和评分逻辑完全不变

## 设计要点

### 1. 调参区分组

调参区明确拆成两块：

#### 基础阈值

用于表达评分的判定边界：

- `collisionThreshold`
- `bigTurnThreshold`
- `windowSize`

#### 评分参数

用于表达评分手感与惩罚强度：

- `collisionPenalty`
- `turnSmoothnessWeight`
- `rangeMatchWeight`
- `gyroStabilityWeight`
- `bigTurnStabilityWeight`
- `speedStabilityWeight`
- `throttleStabilityWeight`

目标：

- 让用户一眼知道“先调哪类参数”
- 降低误把判定边界和评分灵敏度混在一起调的概率

### 2. 布局优化

#### 桌面端

- `基础阈值` 保持较紧凑布局
- `评分参数` 改为双列卡片式排列

#### 移动端

- 自动切换为单列布局
- 每个参数块垂直排列

目标：

- 让参数在手机上更容易逐个阅读
- 避免当前参数增多后出现密集平铺问题

### 3. 文案优化

每个参数项增加极短中文说明，说明只表达调参方向，不解释底层公式。

例如：

- `碰撞阈值`：越小越容易触发碰撞
- `大弯阈值`：越小越容易进入大弯区
- `窗口大小`：越大越平滑
- `碰撞扣分`：每次碰撞扣多少分
- `转弯平滑敏感度`：越大越容易因为抖动掉分
- `区间匹配敏感度`：越大越容易因为动作不协调掉分
- `速度稳定敏感度`：越大越容易因为 pseudoSpeed 波动掉分

目标：

- 帮助现场调参用户快速理解调大调小的大方向
- 避免页面变成公式说明书

### 4. 当前配置摘要

当前配置摘要区域优化为更具可读性的格式，至少突出以下关键值：

- `碰撞阈值`
- `大弯阈值`
- `窗口大小`
- `碰撞扣分`

目标：

- 用户保存后可以立刻看到最关键的当前值
- 方便实车时快速确认当前配置是否已经切换成功

### 5. 状态反馈优化

保存成功时：

- 由当前简短提示升级为更明确反馈
- 明确包含“已写入设备”“重启后保留”这类信息

恢复默认值时：

- 明确提示“已恢复默认值并写回设备”

保存失败时：

- 保持现有错误反馈风格，但文案更清晰

目标：

- 用户在现场不必反复猜测“到底有没有保存进去”

## 实现边界

本轮实现只改 `/judge` 页面前端资产文件。

明确不改：

- `JudgeConfig` 结构
- `NVS/Preferences` 读写逻辑
- `/api/judge-config` 接口结构
- 评分函数内部公式
- WebSocket / HTTP 遥测链路

## 测试与验证

### 源码断言

更新 `tests/test_firmware_feature_flags.py`，重点检查：

- 页面中出现更清晰的分组标题
- 页面中出现关键说明文案
- 页面中出现更清晰的保存/恢复反馈文本

不需要为这轮纯 UI 微调引入复杂新测试。

### 回归验证

继续执行：

- `pytest tests/test_firmware_feature_flags.py`
- `.\arduino-cli-wsl.ps1 -Compile -Sketch MUS4_FW.ino`

目标：

- 确保前端资产改动没有破坏构建
- 确保 `/judge` 页面增强不影响既有集成

## 本轮不做项

- 滑块控件
- 新增参数
- 图形化调参对比
- 参数预设切换
- 调参与实时图表联动增强
- 后端接口调整
- 评分逻辑调整

## 成功标准

- 打开 `/judge` 后，调参区能明显区分“基础阈值”和“评分参数”
- 第二批参数在桌面端和移动端都更容易阅读和操作
- 每个字段都具备短而清晰的中文提示
- 保存和恢复默认值后的反馈更直观
- 本轮改动不影响现有配置读写和评分行为
