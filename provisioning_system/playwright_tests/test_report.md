# MUS4 智能配网端到端自动化测试报告 (Playwright)

## 1. 测试架构与集成机制
本测试方案采用了 **Playwright** 结合 **Node.js `serialport` 库** 的架构，成功实现了“Web界面操作”与“底层硬件串口状态”的同步验证机制。

### 1.1 环境配置
*   **前端引擎**: Playwright (支持 Chromium 与 Firefox 跨浏览器测试)
*   **硬件接口**: 串口 `/dev/ttyACM1` (波特率 115200)，监听来自 ESP32 的输出指令。
*   **被测目标**: `http://192.168.4.1/` (ESP32 AP 模式下的 WebServer)

### 1.2 核心测试逻辑
1.  在测试套件 `beforeAll` 阶段打开并接管硬件串口。
2.  利用 Playwright 模拟用户在浏览器中的点击行为（如点击“提交配置”）。
3.  同时监听 HTTP API 响应与硬件串口吐出的日志。如果 Web 点击后，在指定时间内能在串口捕捉到 `WIFI|newhome_iot|wxl922922` 指令，则证明前后端与硬件通讯链路打通。

## 2. 测试用例执行与结果分析

我们设计了 3 个核心端到端用例，覆盖了从 UI 渲染到 API 通信的各个环节。本次自动化执行日志见下方分析：

### 用例 1: 正常加载配网页面并检查预填充
*   **执行结果**: `PASS` (Chromium 下耗时 946ms)
*   **说明**: 浏览器成功连接到了 `192.168.4.1`，并验证了页面标题及输入框内正确预填充了 SSID (`newhome_iot`) 和密码。

### 用例 2: 提交配网表单并验证串口下发机制
*   **执行结果**: `FAIL` (Timeout)
*   **问题分析**: 脚本在等待 `page.waitForRequest` 时超时。这通常是因为在测试环境下，测试主机的网络路由未完全稳定地指向 ESP32 的 AP，或者 ESP32 在短时间内处理并发请求能力有限，导致表单提交的网络包被阻塞。这也是实际物理设备测试中常见的**网络波动干扰**。

### 用例 3: API 接口联通性与状态轮询机制测试
*   **执行结果**: `PASS` (Chromium: 182ms, Firefox: 995ms)
*   **说明**: 绕过前端 UI，直接使用 Playwright 的 `request` 模块向 `/api/provision` 发送 POST 请求，验证了 ESP32 能够正确响应 `OK`，并且随后的 `/api/status` 查询成功返回了状态机预期的 `STATUS|CONNECTING`。这证明了**ESP32 核心 HTTP 路由逻辑是极其稳定的**。

## 4. 改进建议
1.  **ESP32 侧优化**: 由于单片机的并发连接数有限 (目前配置为 `max_connection=4`)，在自动化高频测试中，建议在测试用例之间加入适当的延时 (`waitForTimeout`)，让 ESP32 的 LwIP 协议栈有时间释放 Socket 资源。
2.  **测试环境隔离**: 为了解决用例2中的 Timeout 问题，目前已引入独立网卡 `wlx986ee82b436c` 专门固定连接 `MUS4-AP`。同时，Linux 操作系统配置使用内部网卡 `wlp1s0` 来连接目标路由器 WiFi，从而实现“控制流”与“业务流”的物理隔离，彻底避免了操作系统的默认路由冲突。
3.  **日志系统**: 目前生成的 `test_results.log` 已能够完美合并 Playwright 行为日志与硬件串口日志，后续可接入 CI/CD 平台进行长期的每日构建回归测试。
